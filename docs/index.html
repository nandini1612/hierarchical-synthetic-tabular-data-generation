Synthetic tabular data · logical validity

Synthetic data that can’t exist in real life — caught and fixed.

Standard metrics grade synthetic data column by column, so a record can pass every check and still be impossible. This is a drop-in layer that flags logically impossible rows and repairs them to zero — with no training, no GPU, and no change to your generator.

By Nandini Saxena & Snigdha Sarkar — extending the H-TDBU framework of Nie, Jin & Chen (2026).

The problem

Statistical fidelity ≠ logical validity

Synthetic-data quality is measured column by column — distributions, correlations, downstream accuracy. None of it asks whether a single row holds together. So a generator can pass every metric and still produce records that could never exist. The framework we build on (H-TDBU) names this problem but never solves it. Here is one real example — three fields that are each fine on their own, and impossible together:

// one synthetic Bank Marketing row

pdays
−1
“never previously contacted”
✓ plausible value
previous
3
“contacted 3 times before”
✓ plausible value
poutcome
success
“a past campaign succeeded”
✓ plausible value
✕ impossible

You cannot have zero prior contacts and also three prior contacts and a past success. Every column passes on its own; the record is incoherent. No existing fidelity or utility metric flags this.

How it works

Three stages, dropped in between generation and scoring

It changes no existing code and does no machine learning — just boolean checks, one similarity lookup, and a loop that settles. That keeps it generator-agnostic and fast. Our additions are highlighted below; the baseline generator and evaluation are untouched.

01 · detector

Violation meter

Hand-written logical rules per schema, each a vectorized boolean test over columns. Reports a new violation_rate the pipeline never had.

boolean arithmetic
02 · repair

Fix, don’t discard

Discarding invalid rows would delete up to 40% of a weak generator’s output. Instead, edit only the offending columns.

two strategies →
03 · loop

Settle to zero

Constraints share columns, so a fix can re-break another. Re-sweep until no violations remain — converges in ≤3 passes.

iterate to fixed point

Stage 2 · two ways to repair

k-NN repair

When a rule has no single right answer, copy the offending columns from the most similar real record. Minimally invasive — but it borrows real data.

Canonical repair

Fix the row using only its own values — e.g. declare it “never contacted.” Reaches the same validity, injects no real data. This is the honest control.

    The key finding

    The “accuracy boost” from repair is really data leakage

    This is the experiment at the heart of the project. On a weak generator, k-NN repair looks like it lifts downstream accuracy. But canonical repair — which reaches the same 0% validity — does not. Same validity, opposite effect. So the movement was never caused by validity; it’s k-NN quietly copying real values into the synthetic set.

    TSTR AUROC · independent generator

    no repair k-NN — copies real data canonical — row-only chance = 0.50

    Both fixers reach 0% violations. Only the one that touches real data “improves” AUROC.

    Before the constraint fix, a critic could say “k-NN gained because it repaired more.” Now both repair everything — so the +0.10 is unambiguously leakage, and honest repair (canonical) even dips slightly.

    Safety & cost

    Free on good generators, and cheap everywhere

    When a generator already preserves column structure (RandomForest, XGBoost), all three modes score identically within seed noise, and cross-modal alignment is untouched. Repair costs nothing here — so there’s no reason to ever turn it off.

    Detection is essentially free; canonical repair is trivial; even k-NN repair is ~1% of a real generator’s runtime (RandomForest takes ~100 s to generate the same rows). The alternative — discarding invalid rows — would throw away 40% of a weak generator’s output.

    The bottom line

    What this actually delivers

    “Logical validity and statistical utility are separable properties, requiring separate mechanisms. Repair’s job is validity — delivered at ~1% compute overhead and no utility cost. It is not a utility booster, and any apparent boost is real-data leakage, which we demonstrate by construction.”

    What it is

    • A validity layer: 11–40% impossible rows → 0%
    • Free & non-interfering on good generators (utility, fidelity, cross-modal alignment all unchanged)
    • Cheap: detection ~7 ms, CPU-only, no training
    • Better than discarding, which loses 40% of the data

    What it is not

    • Not an accuracy improver — deltas sit within seed noise
    • The one apparent gain is provably data leakage
    • Constraints are hand-authored per schema (doesn’t auto-scale)
    • Untested downstream of LLM-based generators — flagged as future work
